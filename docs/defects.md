# Defects - JupyterLab Tabular Data Viewer Extension

`[ ]` open, `[x]` fixed. Dated notes under each track how it evolved.

## Document loading

- [x] `DEF-1` **large database never opens - whole file base64-encoded before the widget runs** - HIGH; opening a 507.6 MB SQLite database takes an enormous time and ultimately fails; cause: `src/index.ts` registers every binary tabular type with `fileFormat: 'base64'` and both widget factories with `modelName: 'base64'`, so `Context` fetches the entire file through `/api/contents` and base64-encodes it before the widget renders - content `TabularDataWidgetFactory.createNewWidget` never reads, since it uses only `context.path`; at 507.6 MB the base64 string is 676,800,000 chars against V8 `MAX_STRING_LENGTH` 536,870,888, i.e. 1.26x the hard limit, so the string cannot be constructed at all; fix: register a no-content model factory with `fileFormat: null`, which makes `Context` request `content: false`; `src/index.ts`
  - 2026-08-09 reported: "reading sqlite db chats.db takes enormous amount of time and fails ultimately"
  - 2026-08-09 measured: `dbstat` puts 299 MB in `profile_photos`, 110 MB in `media`, 81 MB in `feed_scan`; `.nodeenv/bin/node` reports `MAX_STRING_LENGTH` 536,870,888 vs a 676,800,000-char payload
  - 2026-08-09 mechanism confirmed: `node_modules/@jupyterlab/docregistry/lib/context.js:561` gates the content fetch on `content: this._factory.fileFormat !== null`
  - 2026-08-09 prior history: the same discarded-content fetch was measured at ~19 s for a 44 KB database during the v1.7.5 galata work and deferred as a follow-up rather than fixed
  - 2026-08-09 fixed: closed - NoContentModelFactory with fileFormat null; galata asserts on the wire that opening a .db issues no content=1 /api/contents request
- [ ] `DEF-5` **Ctrl+S on an open viewer now raises a File Save Error dialog** - LOW; with `fileFormat: null` the context builds save options `{type:'file', format:null, content:''}` and the contents API rejects them with 'Must specify format of file contents', so Ctrl+S on a viewer tab pops an error dialog where the base64/text models previously round-tripped silently; the file is byte-unchanged and no data is lost, and silently rewriting a 500 MB database from a discarded round-trip was arguably the worse behaviour; `src/index.ts`
  - 2026-08-09 reported: found by bug-hunter review; verified server-side - LargeFileManager.save with format None raises HTTP 400 and leaves the file at 216 B unchanged. Not verified in a live browser
  - 2026-08-09 not fixed in this change - the widget factory already declares readOnly: true but the save command gates on contentsModel.writable, so suppressing the dialog needs a UI-level change with its own risk; deliberately deferred rather than bundled into the cache round
  - 2026-08-09 unverified suspicion carried over from the review: a third-party contents manager that does not validate `format` could take `content: ''` literally and truncate the file; the stock manager rejects it. Settling test is running the same save against whichever non-default manager is supported
  - 2026-08-09 scope note from architect round 2: NoContentModelFactory now passes collaborative=false, which flows into Context.canSave, so under an RTC deployment this dialog appears where the base64 factory's collaborative=true previously suppressed it. Keeping false anyway - a ydoc session over a model that by construction holds no content is the worse option
- [ ] `DEF-20` **a clock-time or elapsed-time column returns 500 on the data request** - MEDIUM; pre-existing; a column arriving as arrow `time64` or `duration` - an Excel cell formatted as a time or an elapsed time - makes the rows request fail with a 500 and a traceback, while the statistics request on the same column succeeds; cause: `convert_to_json_serializable` (`routes.py:34`) handles `date`, `datetime`, `Decimal` and `bytes` but not `datetime.time` or `datetime.timedelta`, neither of which subclasses `date`, so the value reaches `json.dumps` and raises `TypeError`; measured identical at HEAD with pandas (`time64[us]`, `duration[us]`, same `TypeError`), so it is not a polars regression and sits outside DEF-4; `routes.py`
  - 2026-08-11 reported: surfaced by the round-4 adjudication as a candidate regression and disproved as one: reproduced against v1.7.11's pandas cascade on the same fixture. Recorded on the user's call because the round-4 tests now advertise time and timedelta cells, so a later probe would hit it and misattribute it to the polars swap

## SQLite reader

- [x] `DEF-2` **BLOB bytes read into memory only to be replaced by placeholders** - HIGH; `_read_sqlite` issues `SELECT * FROM "t"` and then maps `_blob_placeholder` over object columns in pandas, so every BLOB is fully materialised before being discarded; on the reported database that is ~410 MB of pointless I/O per request for `profile_photos` and `media`; fix: build the select list from `PRAGMA table_xinfo` filtered on `hidden != 1` and wrap each column so the placeholder is produced in SQL, leaving the bytes in SQLite; `jupyterlab_tabular_data_viewer_extension/readers.py`
  - 2026-08-09 reported: user directive "do not bring blobs to frontent just put placeholder"
  - 2026-08-09 measured: arrow output for `profile_photos` is 319,717 bytes from a 299 MB table, confirming the bytes are read and thrown away
  - 2026-08-09 verified: on a generated 134 MB database holding 128 MB of BLOBs the placeholder path costs 0.004 s and +5 MB RSS, while forcing the payload to be read (CAST to BLOB) costs 0.059 s - 14x, so LENGTH() is answered from the record header and this is not a page-cache artifact
  - 2026-08-09 fixed: closed - placeholders built in SQL, payload never leaves SQLite; 0.004 s and +5 MB RSS on a 128 MB BLOB table
  - 2026-08-09 behaviour change found by bug-hunter review: the Python formatter and the new SQL disagreed on 5,118 sizes because SQLite's printf rounds half away from zero while CPython's %.1f rounds half to even - a 1,280-byte BLOB rendered '1.3 KB' from SQL and '1.2 KB' from Python. The docstring claiming they matched was false. Resolved by deleting the Python twin (already dead in production) and keeping half-up; sizes at exact binary halves now render one digit higher than in 1.7.6
  - 2026-08-09 correction to the fix clause above: PRAGMA table_info was the wrong instrument - it omits STORED and VIRTUAL generated columns that `SELECT *` returns, so it silently dropped them from the grid. The shipped select list is built from PRAGMA table_xinfo filtered on hidden != 1, which reproduces `SELECT *` across ordinary, generated, fts5 shadow, rtree, geopoly, STRICT and WITHOUT ROWID tables
- [x] `DEF-3` **no progressive load - every request re-reads the whole table** - MEDIUM; all five handlers call `read_as_arrow_table`, so metadata, each page, column stats, unique values and download each perform a full `SELECT *`, with pagination applied only after the read; `feed_scan` costs 0.93 s and 66 MB of arrow per request; fix: metadata fast path via `PRAGMA table_info` + `COUNT(*)`, and `LIMIT`/`OFFSET` pushdown on the unfiltered and unsorted browse path, falling back to a full read when filters or sort are active; `jupyterlab_tabular_data_viewer_extension/routes.py`
  - 2026-08-09 reported: "feels like we do not follow the progressive load rule and filter/ stats executed on full"
  - 2026-08-09 measured: per-table `_read_sqlite` cost across all 15 tables totals ~1.3 s, peak RSS 570 MB; slowest single table `feed_scan` 0.93 s
  - 2026-08-09 scope note: filter pushdown is deliberately excluded - the frontend offers regex filters and SQLite has no `REGEXP` operator by default, so pushing filters into SQL would change matching behaviour
  - 2026-08-09 attempted: LIMIT/OFFSET pushdown on the unfiltered and unsorted path, plus `COUNT(*)` for the row total - did NOT work; pandas infers dtype from the rows it is handed, so a window disagrees with the full table. A nullable INTEGER column reads back int64 from a 10-row non-null window and float64 from the full table, rendering 0 on one page and 0.0 on another. Reverted
  - 2026-08-09 attempted: gating the pushdown on a single-pass type-stability probe (85 ms over feed_scan's 31 columns) - did NOT work either; requiring one storage class and no NULLs per column disqualifies every table in the reported database (feed_scan 18/31 nullable, profiles 17/30, profile_scan also mixed), so the gate would never fire and the probe would be pure cost
  - 2026-08-09 attempted: metadata fast path via PRAGMA table_info - rejected before implementation; PRAGMA reports SQLite declared types (INTEGER/REAL) while the frontend matches arrow type names and isNumeric() substring-matches them, so it would change displayed types and numeric filter behaviour
  - 2026-08-09 stays open: invariant pinned by test_nullable_column_type_is_stable_across_any_row_window so a future attempt cannot reintroduce the mismatch silently; residual cost is a 0.735 s full read per page on feed_scan
  - 2026-08-09 fixed by caching instead: read_as_arrow_table now caches the arrow table on (abspath, sheet, mtime_ns, size) in a 256 MB LRU. Filters, sorting and stats stay global and the page is cut from the identical table object, so the windowed-inference mismatch cannot arise. Measured on the reported database: feed_scan 633.7 ms -> 0.03 ms, profile_photos 91.8 ms -> 0.03 ms; four tables resident in 78 MB
  - 2026-08-09 fixed: closed - repeat reads served from memory; 72 pytest green
  - 2026-08-09 correction: the claim that test_nullable_column_type_is_stable_across_any_row_window pinned the invariant was FALSE as written - the test only read the full table and never took a window, so a reintroduced pushdown would have left it green. Found by architect review; the test now reads a LIMIT 10 window through the same \_df_to_arrow path and asserts the int64/double disagreement explicitly
- [x] `DEF-4` **pandas must be removed from the read and export paths** - MEDIUM; pandas is the reader engine for every format (`pd.read_sql_query`, `pd.read_csv`, `pd.ExcelFile`) and the export engine in `DownloadHandler`; it also promotes a nullable INTEGER column to float64, so such a column exports as 42.0 rather than 42, and it is what made a windowed read disagree with a full one; fix: polars as the reader and export engine, openpyxl kept for reading .xlsx and xlsxwriter added for writing it, preserving the v1.6.0 mixed-type cascade and the exact export content types; `jupyterlab_tabular_data_viewer_extension/readers.py`
  - 2026-08-09 reported: reported: user directive "and pandas must be killed"; staged after the cache so the reader-engine swap reviews independently
  - 2026-08-09 measured: raw pyarrow and polars both keep a nullable INTEGER column at int64 across a window and a full read, where pandas gives int64 vs float64 - confirming the promotion is a pandas artifact. Both still disagree on a genuinely mixed-storage-class column, which is inherent to windowed inference
  - 2026-08-09 note: this repo has never used polars despite the workspace convention - declared deps are pyarrow>=10.0.0, pandas>=1.5.0, openpyxl>=3.0.0; polars 1.43.2 is present in the environment only
  - 2026-08-10 decided: polars over pyarrow-native, per user; fastexcel turned out NOT to be needed, since polars reads .xlsx through the already-declared openpyxl engine, so the swap adds polars and xlsxwriter (~200 KB) and drops pandas
  - 2026-08-10 measured: polars carries the v1.6.0 cascade natively on all three source types, keeps a nullable INTEGER at int64 across a window and a full read, supports latin1 CSV directly, and normalises pyarrow `string_view` on the way in - so `pl.from_arrow` is safe on the parquet fixture that broke stats in v1.5.12
  - 2026-08-10 correction: the claim in this defect that a promoted column "displays as 42.0 rather than 42" was FALSE. Verified by mutation: reintroducing the float cast in the installed reader left a grid-based assertion green, because the backend serialises 42.0, JSON has one number type and JavaScript renders it "42". The promotion is visible in the EXPORTED file, not the grid - a CSV export writes 42.0 - so the galata test asserts exported content and the defect line is reworded
  - 2026-08-10 caught in own work: `infer_schema_length=None` is load-bearing on the CSV and SQLite reads and nothing tested it - every mixed fixture here is a few rows long, so polars' default 100-row window covered them all. A string past row 200 raises ComputeError; now pinned by test_mixed_column_resolves_when_the_string_arrives_late, mutation-verified to fail when the argument is dropped
  - 2026-08-10 fixed: readers.py and DownloadHandler are pandas-free, deps swapped in pyproject.toml, guarded by test_extension_does_not_import_pandas (subprocess check, since pytest's own plugins import pandas into the shared interpreter)
  - 2026-08-10 follow-up: the swap left one cosmetic export difference unfixed, tracked as DEF-6
  - 2026-08-10 correction to the note above: the subprocess rationale was wrong - neither pytest nor any test in the file imports pandas, so sys.modules here would be clean. The subprocess is still right, but because an in-process check would pass or fail on whatever else imported pandas first; the test docstring now says that
  - 2026-08-10 adversarial review found four regressions the swap introduced, all fixed and each now pinned by a mutation-verified test: a 0-byte or ragged csv returned 500 instead of 400 because no polars exception subclasses ValueError; polars' read_excel defaults dropped blank columns and rows and raised on an empty sheet; list_excel_sheets offered chartsheets as unopenable tabs; and a binary column made write_ndjson panic in Rust, which inherits BaseException and so escaped the handler's except Exception and left the request with no body
  - 2026-08-11 round-4 review (architect + bug-hunter, both DO-NOT-SHIP) found four more, all reproduced independently before fixing and all VALUE-level rather than layout-level, which is why the 8-shape layout comparison and the 784-case sweep both missed them. `_value_kind` had grouped date, datetime, time and timedelta as one 'temporal' kind, so the mixed-kind guard never fired on the mixtures that need it: datetime+time and date+time raised ComputeError (400, file unopenable), datetime+timedelta silently nulled the duration, and time+timedelta reached arrow as fixed_size_binary[8] holding raw CPython object pointers, which the grid rendered as mojibake and every export wrote as hex. Six of Excel's seven error values retyped a numeric column to text where pandas mapped a TYPE_ERROR cell to NaN. Polars infers Int128 for an integer at or above 2**63 in a csv (above 2**64 via a spreadsheet cell) and pyarrow cannot consume its arrow export, so ArrowInvalid('\_pli128') - itself a ValueError - made such a file a 400. And fix 6 was half applied: `list_excel_sheets` still handed openpyxl a path, and the metadata handler calls it BEFORE the reader, so an xlsx named .xls still 500d - the reader-only test was green over a broken path. Fixed with one kind per widenable type set, an Excel-only error-value set, an Int128 recast in the shared cast helper, and a file handle at both openpyxl call sites; 141 pytest green, 29 of 29 mutations killed across four rounds

## Export

- [ ] `DEF-6` **Excel date column exports with a spurious zero time** - LOW; a timestamp column read from .xlsx exports to csv and tsv as `2023-02-25T00:00:00.000000` where pandas wrote `2023-02-25`; cause openpyxl returns datetime for a date-formatted cell and polars' csv writer always emits full ISO form, whereas pandas dropped a zero time component; fix not applied - either cast a timestamp column whose times are all zero to Date, or pass an explicit `datetime_format`, both of which reach beyond the pandas swap; `routes.py`
  - 2026-08-10 reported: found while verifying the export-parity claims for the pandas removal (DEF-4); reproduced on data/sample_data.xlsx join_date
- [ ] `DEF-8` **a decimal256 column cannot be exported in any format** - LOW; a parquet holding a decimal column of precision above 38 browses and reports statistics normally, then every export returns 500; cause `pl.from_arrow` panics in Rust with `operator does not support primitive Int256` before the format branch, so parquet dies with the rest; regression - pandas exported it as `1.25`; fix not applied - restoring it means an arrow-side cast to decimal128 or string that no other type needs, and precision above 38 does not fit decimal128 at all; `routes.py`
  - 2026-08-10 reported: found by bug-hunter review of the pandas removal (DEF-4); until the PanicException arm was added this left the request with no status and no body at all, which the frontend could not report
- [ ] `DEF-9` **nested and duration columns no longer export to csv or tsv** - LOW; a parquet column of type list, struct, map or duration returns 500 for csv and tsv; cause polars' csv writer raises ComputeError on all four; jsonl is unaffected and writes them (`{"a":[1,2]}`, `"PT1S"`), except for a Binary nested inside a List or Struct, which the top-level hex cast does not match and which panics in write_ndjson; regression - pandas wrote a representation for each (`[1 2]`, `{'a': 1}`, `[('k', 1)]`, `1 days`); fix not applied - a faithful serialisation needs a different expression per type, which costs more than the defect; `routes.py`
  - 2026-08-10 reported: found by architect and bug-hunter review of the pandas removal (DEF-4); the round-1 decline claiming pandas also failed here was wrong, measured. The grid already 500s on such a column, so reaching this needs a hand-built request
- [ ] `DEF-14` **xlsx export loses the sign of an infinity** - LOW; a float column holding +inf and -inf writes both as the same `#DIV/0!` error cell, so the two become byte-identical; cause xlsxwriter maps every non-finite float to that error; pandas wrote the text 'inf' and '-inf'; fix not applied - it needs a pre-pass over float columns for a value parquet rarely carries; `routes.py`
  - 2026-08-11 reported: found by the pandas differential sweep for DEF-4
- [ ] `DEF-15` **a null in a single-column csv export writes a bare blank line** - LOW; a one-column numeric table with a null exports as `v\n1.5\n\n`, which any consumer skipping blank lines reads as one row; cause polars writes an unquoted empty field where pandas wrote `\"\"`; multi-column tables are unaffected, having a delimiter on the line; fix not applied - `quote_style` would change every other cell's quoting; `routes.py`
  - 2026-08-11 reported: found by the pandas differential sweep for DEF-4; the extension's own reader still recovers both rows

## Excel reader

- [ ] `DEF-7` **second and later blank CSV headers are named \_duplicated_0 rather than Unnamed: N** - LOW; a csv with more than one blank header yields columns named `Unnamed: 1`, `_duplicated_0`, `_duplicated_1` where pandas named every one `Unnamed: <position>`; cause polars leaves only the first blank header empty and names the rest itself, and `_name_unnamed_columns` rewrites only the empty one; fix not applied - a synthesised name cannot be told apart from a column a file genuinely carries under it, so renaming would silently rewrite real headers; `readers.py`
  - 2026-08-10 reported: found by probe while verifying the DEF-4 blank-header fix; no functional impact - every column still reaches the frontend with a non-empty name, pinned by test_excel_every_blank_header_gets_a_usable_name
  - 2026-08-11 narrowed to csv only: the Excel reader now builds its own header names, so every blank worksheet header is numbered positionally exactly as pandas numbered it. Verified on a sheet with three blank headers
- [ ] `DEF-17` **whole number stored with a decimal point reads as float** - LOW; a cell whose stored value is `1.0` reads as float64 and exports with a `.0` tail, where pandas' `_convert_cell` coerced it to int64 (pandas/io/excel/\_openpyxl.py:606); cause: the reader takes openpyxl's raw float rather than testing `int(v) == v` per cell; wontfix-deliberate: the file's own stored value is `1.0`, so writing `1.0` is the faithful reading and pandas' coercion is the divergence; neither Excel nor openpyxl emits this form, so it needs a third-party writer to reach; `readers.py`
  - 2026-08-11 reported: reported by round-4 review with a byte-level fixture; not reproducible through openpyxl's writer, which normalises a whole number to <v>1</v>
- [ ] `DEF-18` **.xls is claimed by the backend but registered by no frontend file type** - LOW; the backend types `.xls` as excel and both openpyxl call sites now open one, but `docRegistry.addFileType` registers only `.xlsx` (`src/index.ts:269`), so no file-browser route delivers a `.xls` path to the handlers and the viewer is never offered for one; cause: `get_file_type` has claimed the extension since before the polars swap while the frontend never did; a genuine legacy BIFF `.xls` would still fail - openpyxl reads only the zip-based format and xlrd is not a dependency; `src/index.ts`, `readers.py`
  - 2026-08-11 reported: surfaced by the round-4 review while fixing the xlsx-named-.xls 500. Recorded rather than fixed: registering the extension would advertise support for legacy BIFF files this extension cannot read, and was not asked for
- [ ] `DEF-19` **a text cell spelling an Excel error code reads as missing** - LOW; a cell whose literal text content is `#REF!`, `#DIV/0!`, `#VALUE!`, `#NAME?`, `#NUM!` or `#NULL!` now reads as missing, where pandas kept the string; cause: `iter_rows(values_only=True)` discards `cell.data_type`, so the reader cannot tell a real error cell from text spelling the same code and matches on the string set (`_EXCEL_ERRORS`, `readers.py:129`); `#N/A` is unaffected, it was already in pandas' missing-value set; wontfix-deliberate: the divergence is narrower than the one it fixes - a real broken formula retyped its whole column - and reading `data_type` instead of `values_only` would rewrite the read loop with its trim, header and kind logic; `readers.py`
  - 2026-08-11 reported: accepted cost of the round-4 broken-formula fix, surfaced by the round-4 adjudication rather than by a lens
